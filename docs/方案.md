# 给 Codex CLI 用的多渠道聚合本地网关 —— 方案

> 目标：把 [dsh-our-free-model](https://github.com/Ebony-Vinyl/dsh-our-free-model) 的「多渠道聚合」思路
> 与 [Codex-Manager](https://github.com/qxcnm/Codex-Manager) 的「本地网关转发多账号」思路合并，
> 做出一个**独立应用**，让 **Codex CLI** 直接使用多家渠道
> （TRAE / Cline / Qoder / ZCode / Loomy / Raccoon / MiniMax / Gemini / CodeArts / LobsterAI
> + Kilo 免密车道 + 自带 API Key 的 provider 目录），而不是只切 ChatGPT 账号。

---

## 〇、最终形态（与最初设想不同，说明一下）

最初设想是「改造 dsh 插件仓库，加一层 failover」。**实际做下来是另一回事**：

| | 最初设想 | 最终形态 |
|---|---|---|
| 交付物 | dsh 插件的一个分支 | **独立 app**（`ofm-codex-gateway/`） |
| 渠道从哪来 | 插件运行时提供 | **vendor 进 app**（约 8600 行） |
| 网关 | 转发给插件的 standalone | **自建** Responses 端点 |
| GUI | 无 | Electron 桌面壳 + 内置 Web 界面 |

**为什么改**：最初我想的是「在 dsh 插件仓库里加一层 failover」。
但插件是**给 DSH 宿主用的** —— 它的价值是「让 DSH 的用户多一条路」，
而这里的目标是「给 Codex CLI 一个能用的 app」，**用户里没有 DSH**。

换句话说，插件形态解决的是「DSH 用户怎么用 Codex 渠道」，
而实际要解决的是「Codex 用户怎么用这些渠道」。这两件事的**分发单元**不同。

改成 app 之后：
- 渠道适配直接 vendor 进 app（约 8600 行），**运行时零 DSH 依赖**
- 用户只需要装这一个 app，不需要 DSH、不需要装插件
- 插件仓库后续怎么改都不影响这个 app

**验证**（见下文「自包含性验证」）：把 app 目录单独复制到别处，
在没有 node_modules、没有 dsh 仓库的目录里，照常启动并完成推理。

**保留下来的**（下文详述）：
- dsh 的渠道适配（12 家账号渠道的逆向封装）——直接 vendor
- dsh 的账号池、限流感知、失败分类 ——直接 vendor
- Codex-Manager 的轮换 / 冷却 / 会话粘性设计 ——**照抄**（本仓库 `src/route.js`）
- Codex-Manager 的 config.toml 接入契约 ——照抄

**丢弃的**（见下文「明确不做的事」）：免费聚合线与 EAC 共付车道 ——
它们靠**冒充官方客户端**工作。

## 一、结论先行

**这个方案可行，而且比预想省力得多。** 关键发现：

| 事实 | 影响 |
|---|---|
| dsh 的两套网关**都已经实现了 `POST /v1/responses`** | Codex CLI 唯一需要的端点，不用写 |
| dsh 的 `toResponsesGenerateOptions` **已实现 Responses → chat/completions 请求方向改写** | 正是 Codex-Manager 缺的那块洞 |
| dsh 的 channel-pack `responses.ts` 注释里**明确写着「新一代客户端（Codex CLI）只认 Responses」** | 作者已经踩过 Codex 的坑，包括 usage 口径 |
| Codex-Manager 缺 Responses→chat 改写、缺多渠道概念（只有 ChatGPT 账号） | 它的**轮换/冷却/粘性**层值得抄，**渠道层**要换成 dsh 的 |
| **上游 v2.5.8 已内置 Codex CLI 接入配方**（`index.js:2136` 的「接入客户端」分区直接生成 `config.toml`：`model_provider="ofm"` + `wire_api="responses"` + `env_key`） | 「Codex 适配」阶段几乎归零，**只剩跨 provider failover 要新写** |

**所以分工是明确的：**
- **协议层 + 渠道层 → 用 dsh 的**（已经跑通，是现成的）
- **轮换/容错/接入层 → 抄 Codex-Manager 的**（dsh 这块偏弱，Codex-Manager 这块很强）
- **要新写的 → 只有一个核心缺口：把 dsh 的两条线合流成统一路由（provider 级 failover）**

### 已实测验证（本机跑通）

```
$ node packages/standalone/cli.mjs --port 18900 --data-dir /tmp/ofm-test --no-refresh
$ curl http://127.0.0.1:18900/health
{"ok":true,"capabilities":{"anonymous":true,"accountChannels":true,...}}

$ curl -H "Authorization: Bearer $KEY" http://127.0.0.1:18900/v1/models
{"object":"list","data":[{"id":"mimo-v2.6-flash-free",...}]}      # ✅ 通

$ curl -X POST .../v1/responses -d '{"model":"...","input":"hi","stream":true}'
```

（匿名免费车道当前被限流，这正是要用多账号渠道解决的问题。）

## 二、两个仓库的定位

### dsh-our-free-model —— 协议与渠道层（复用主体）

**三条互不相干的技术线**，这点必须分清：

| 线 | 目录 | 内容 | 对我们的价值 |
|---|---|---|---|
| **免费聚合线** | `src/*.js` | `opencode.ai` 免密网关（`Authorization: Bearer public`） | 中：协议转换齐全，但单池无账号 |
| **渠道包线** | `vendor/channel-pack/src/*.ts` → `packages/standalone/channels/business.mjs` | **13 家客户端私有 API 的逆向封装**，含完整账号池 | **高：主体** |
| **provider 目录** | `src/providers/registry.json` | **75 个 provider**（用户自填 Key），4 种协议格式 | **高：补充** |

**渠道包 13 家**（`business.mjs` 的 `modelAdapters`）：

| provider | 上游协议 | 鉴权 | 登录方式 |
|---|---|---|---|
| `codearts` | OpenAI 兼容 | Bearer + `x-ide-*` | 本地回调 |
| `lobsterai` | OpenAI 兼容 | `X-LobsterAI-Client-*` | 本地回调 |
| `qoder` / `qodercn` | OpenAI 兼容 | Bearer | PKCE 设备码轮询（404=未授权） |
| `trae` | **私有 SOLO 协议** | `Cloud-IDE-JWT` | 回调 / PKCE |
| `cline` | 标准 OpenAI | `Bearer workos:<jwt>`（前缀不可剥） | WorkOS 设备码 |
| `loomy` | OpenAI 兼容 | **`token:` 头**（不是 Bearer！） | 微信登录 |
| `raccoon` | OpenAI 兼容 | Bearer | 扫码 |
| `minimax` | OpenAI 兼容 | Bearer | OAuth |
| `gemini` | **Gemini generateContent** | OAuth | OAuth |
| `zcode` | **纯 Anthropic Messages**（openai 路径 404） | Bearer + captcha | 验证码载体页 |
| `opencode` | OpenAI 兼容 | 匿名 + 指纹 | 免登录 |

**75 个 provider 目录**按协议分 4 类：`openai-chat`（~68）、`anthropic-messages`（anthropic/glm/minimax-cn）、
`openai-responses`（openai_api/openai）、Vertex 特殊。category 分 `apikey`(~50) / `free-tier`(~12) / `local`(3) / `oauth`(2)。

### Codex-Manager —— 轮换与接入层（借鉴对象）

Rust workspace。它是**「多 ChatGPT 账号」**，不是「多渠道」：账号表存 `issuer`/`chatgpt_account_id`/`workspace_id`，
上游硬编码 `chatgpt.com/backend-api/codex`，出站头带 `chatgpt-account-id`。

但它的**网关工程**做得很好，是我们要抄的部分。

### ❌ 必须新写

| 需要 | 缺口 | 建议 |
|---|---|---|
| **provider 级 failover**（核心） | dsh 的 `nextAccount` 只在**同一 provider 内**换号；`combo:` 轮换是**模型链**不是 provider 链 | 新写 `nextRoute(model, tried)`：候选 = 所有提供该 model 的 provider × 该 provider 的可用账号。**借用 `runCombo()` 的提交规则** |
| **两条线合流** | dsh standalone 按**模型名前缀分流**（`channels.handles(model) ? channels.complete : core.complete`） | 统一成 `provider/model` 命名空间 + 单一 route 解析器 |

| **Codex 专用 profile** | `responses.ts` 是通用 Responses | 加薄层 profile（`reasoning.effort` 档位映射、`parallel_tool_calls`、事件裁剪），**不另写端点** |
| **凭据加密** | Codex-Manager **token 明文存储**（明显安全欠债） | 用 macOS Keychain 或 AES-GCM |

## 五、Codex CLI 接入

### 上游已内置配方 ✅

v2.5.8 的 `index.js:2136` 「接入客户端」分区**已经生成 Codex 的 `config.toml`**：

```toml
# ~/.codex/config.toml
model_provider = "ofm"
model = "<某个 provider/model>"

[model_providers.ofm]
name = "Our Free Model"
base_url = "http://127.0.0.1:18900/v1"
wire_api = "responses"          # ← 关键：告诉 Codex 用 Responses 协议
env_key = "OFM_API_KEY"
```

即：**开箱即用，不需要我们自己写 Codex 适配**。用户在网关页复制配方即可。

### 可选增强（Codex-Manager 风格）

Codex-Manager 用的是另一种写法（`requires_openai_auth` + `experimental_bearer_token`），
好处是**不需要设环境变量**，密钥直接写在 config 里：

```toml
model_provider = "cm"
model = "cline/glm-5"          # 或任一 provider/model

[model_providers.cm]
name = "cm"
base_url = "http://127.0.0.1:48760/v1"
wire_api = "responses"
requires_openai_auth = true
experimental_bearer_token = "<网关 API Key>"
```

契约来自 Codex-Manager 的 `codex_profile.rs:2968`（`PROVIDER_ID = "cm"`），已验证是 Codex CLI 支持的标准格式。
两种写法都可用，建议保留上游的 `env_key` 版（更干净），另提供 `experimental_bearer_token` 版作为备选。

> ⚠️ **切换 provider 时必须同步修历史会话**：Codex 的 `state_5.sqlite` 里 `threads.model_provider` 记着旧 provider，
> 不改会导致旧会话用新 provider 加载时报错。Codex-Manager 的 `history_repair` 已经处理了这个，值得照抄。

## 六点五、实现过程中实际踩到的坑

> 前五个坑来自两个上游仓库的注释；这六个是**本次实现时自己踩的**，
> 都已修复并有对应测试兜着。

### 6. `content-length` 必须剥离，否则请求**永久挂起**

转发请求时若把客户端的 `content-length` 原样带给上游，而 body 已被重新序列化
（换了 model 名、重新 JSON.stringify），长度就对不上了。
`fetch` 按旧长度发、上游按新长度等 —— 两边僵持，
表现为**请求一直挂着直到客户端超时**，而不是干脆报错。

⚠️ **这个坑用 curl 测不出来**：curl 会自己算长度，所以手工验证一切正常；
只有 Node fetch 转发才会挂。测试因此必须用 `fetch` 而不是 `curl`。

同理要剥的还有 `host`（上游是另一个地址）与标准 hop-by-hop 头
（`connection` / `transfer-encoding` / `keep-alive` / `upgrade` / `te` / `trailer`）。

**修复**：`src/gateway.js` 的 `stripHopByHop()`。

### 7. 上游的错误结构不能当字符串塞进 message

基座返回的是标准 OpenAI 错误结构：

```json
{"error":{"message":"...","type":"rate_limit_error","code":"RATE_LIMIT","param":null}}
```

若把整段 JSON 当 message 塞进新的 Error，客户端看到的就是一坨转义过的字符串，
而且**状态码也丢了**（上游 404 变成 502）。Codex 靠 429 区分「限流，稍后重试」
与 4xx（请求本身有问题），状态码丢了它就会误判。

**修复**：`upstreamError()` 解析出 `message` / `type` / `code` / `status` 并原样透传。

### 8. HTTP 200 里也可能带 error 结构

基座的非流式路径在某些情况下会返回 **HTTP 200 + body 里带 `error`**。
只看 HTTP 状态码会把它当成功。必须同时检查 body。

**修复**：非流式路径解析 `payload.error`，并按 `code` 推断状态码
（`RATE_LIMIT` → 429，`invalid_request_error` → 400）。

### 9. `session_id` 与 `Session-ID` 要归一化

头名归一化如果只做「转小写」，`session_id` 和 `Session-ID` 仍是两个不同的头
（一个下划线一个连字符）。会话粘性因此失效 —— 表现为同一会话在不同 provider 间跳。

**修复**：归一化时把 `-` 和 `_` 统一。

### 10. 基座的失败有两种表达，要归一

- 抛异常：`throw Object.assign(new Error(...), { statusCode: 404 })`
- 返回结构：`{ error: '消息', failure: { code, status, retryAfterMs } }`

不归一的话，分类/冷却/抛出三处会各自处理一半，行为不一致。

**修复**：`toError()` 统一成 Error，并保留 `status` / `code` / `retryAfterMs`。

### 11. reasoning 到底算不算「已提交」——两处判据不同，不能混用

基座 `src/forward.js:650` 的 `hasContent` **把 reasoning 算进去**，
但它用于「何时提交 HTTP 响应头」（发出去就不能再换路）；
而本项目要判的是「何时允许换路」（还没真正开始回答就还能换）。

若照抄基座的判据，「模型想了一分钟然后撞配额墙」就永远换不了路 ——
而这正是 Codex 场景下最常见的失败模式。

**修复**：`isAnswerBearing()` 只认 `text-delta` 与 `tool-call-delta`。
两处判据的差异在代码注释里写明了原因，避免后人「顺手对齐」。

## 六点八、vendor 的实际做法与裁剪决策
> 前面讲的是「要做什么」，这一节讲「做的时候具体怎么落地」。

### vendor 了什么

```
vendor/channels/     渠道包（2.6MB 打包产物 + contracts/credentials/images）
vendor/channels/messages.js   消息格式转换（430 行）
vendor/channels/tool-names.js  从 upstream.js 挑出的三个纯函数
vendor/lanes/        http.js（错误分类 + SSE 读取）、egress.js（出口/代理）
vendor/lanes/kilo.js、aggregate.js、catalog.js
vendor/providers/    75 个 provider 的目录与解析
```

约 8600 行。

### 裁掉了什么，为什么

| 裁掉 | 原因 |
|---|---|
| `upstream.js` 整个文件 | 它是**免费聚合线**的实现：伪装官方 opencode 客户端的 UA（`opencode/latest/2.0.26/cli`）、把 `read`/`shell` 工具定义逐字抄官方客户端、session id 按官方时间铸造算法生成、还要现场铸造成对 ID。**冒充客户端不成立。** |
| `upstream.js` 里的 `postStreamed` / `getJson` | 只服务免费线（带指纹头发包），Kilo 与聚合各有自己的发包逻辑 |
| `catalog.js` 的免费线部分（`buildCatalog` / `CAPABILITIES` / `isFreeLane`） | 免费线的模型能力表。裁掉后 606 行 → 302 行 |
| `catalog.js` 的 EAC 部分（`buildEacCatalog` / `isEacEntry`） | 共付车道，凭据来自 seal 包提取的共享签名密钥 |
| `upstream.js` 的三个纯函数 → 单独成 `tool-names.js` | `messages.js` 只需要 `baseModelId` / `restoreToolName` / `MAX_TOOL_NAME_LEN`，不需要整个 upstream.js |

### 裁剪时踩的一个坑

第一版把 `isDisabledLaneEntry` 写成「**没有 `channel` 标签 ⇒ 就是免费线**」。
这会**误杀**测试自造的合成条目（`truncation-test.mjs` 的 `test-model-free` 没有标签）
以及任何合法来源的无标签条目。

**修正**：改为**显式标记** —— `buildCatalog` 给免费线条目打 `channel: 'free'`，
判定只认 `free` 与 `eac` 两个明确值。缺标签的条目按「非停用车道」处理。

这个坑说明：**「缺省即某类」这种隐式推断，在有多种来源的目录里几乎总是错的。**

### opencode 通道的硬性禁用

`vendor/channels/business.mjs` 是打包产物，改不了源码。所以
`vendor/channel-pack/src/index.ts` 里做了两处修改并重新打包：

1. `apply()` 里的 `disableOpencode` 变成**局部常量 `true`**，不再读 `config`
2. RPC 注册时显式传 `disableOpencode: true`（不传的话，调用方能把它改回 false）

**理由**：留一个能靠改一个布尔值就复活的开关等于留后门。
真要复活，必须改动那行常量 —— 那会是一次带着「为什么」的有意识决定。

### Electron 版本

Electron 33 内置 Node 20.18，而内联的 undici 8 需要 `webidl.util.markAsUncloneable`
（Node 20 后期才加）→ 启动即崩。**升到 Electron 45**（内置 Node 22）解决。

## 七、五个必须避开的坑（都是上游代码注释里踩过的）

1. **「先看到 reasoning 再失败」必须能 failover** —— dsh `adapter.js` L215：reasoning-delta **不算提交**，
   否则「想了一分钟然后撞配额墙」这个最有价值的 failover 场景无法触发。Codex 恰恰会先吐 reasoning。
2. **限流解禁时间取更长者** —— dsh `business.mjs` L30842：各家限流解析有「解析不出→退兜底值」的末端，
   而兜底通常是短的（cline 兜底 1 小时，真实可能 19h39m），后写的短值会覆盖先写的真值 → 无限循环。
3. **凭据 ref 前缀按长度降序** —— dsh L29823：`QODERCN` 必须排在 `QODER` 之前，否则 CN 凭据静默挂到 qoder 面板。
4. **usage 的 `input_tokens` 必须含缓存** —— dsh `responses.ts` L30：官方口径含缓存；发不含缓存的会让 Codex
   把缓存算成负输入、上下文占用少算上百倍、**自动压缩永不触发**。
5. **不要用状态码判断设备码「未授权」** —— Qoder 看 HTTP 404，Cline 看响应体 `error === 'authorization_pending'`
   （状态码可能非 2xx）；`slow_down` 必须真的退避否则被 WorkOS 限流。

## 八、风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| **逆向 API 会失效** | 13 家渠道是私有 API，厂商改接口即失效 | 渠道层已隔离在 `business.mjs`；优先用 `format` 标准的渠道 |
| **合规性** | 绕过客户端官方客户端白嫖额度 | 仅供个人研究；注意各渠道 ToS；账号渠道要自己承担风险 |
| **账号安全** | Codex-Manager 明文存 token | 阶段 1 就改 Keychain |
| **上游工程质量** | dsh 的 `business.mjs` 是 2.7MB 打包产物，`src/` 才是可读源码 | 改动在 `vendor/channel-pack/src/` 侧做，改完跑 `npm run channel-pack` 重新打包 |
| **Codex 私有扩展** | `namespace`/`custom`/`tool_search` 工具 dsh 已能摊平，但 Codex 后续可能再加 | 保持「能表达就摊平，表达不了就丢弃+记日志」而非报错 |

## 九、备选方案对比

| 方案 | 工作量 | 能力 | 评价 |
|---|---|---|---|
| **A. dsh 主体 + 抄 Codex-Manager 轮换**（推荐） | 5-7 天 | 13 渠道 + 75 provider + 账号池 + Codex 原生协议 | 协议层已现成，唯一核心缺口是 provider 级 failover |
| **B. 纯 Codex-Manager 加渠道层** | 10-15 天 | 同上 | 要重写 Responses→chat 改写、13 家渠道逆向、账号池，工作量翻倍 |

**推荐 A**，分阶段交付：阶段 0-1 先能用（多渠道账号 + Codex 接入），阶段 2 再补齐智能路由。
